# protocol-changelog

## v1.0 → v1.1

- **type: schema** — Added `SessionCurrentState` enum (`Idle`, `Working`, `WaitingInput`) and `SessionState` struct (`current_state`, `last_event_kind`, `last_event_at_ms`) for per-session current-state projection. Story 1.6, FR25.
- **type: schema** — Added `protocol::rest::SessionListItem` (`source`, `session_id`, `current_state`, `last_event_kind`, `last_event_at_ms`, `updated_at`) — list-shaped row for `GET /sessions` responses. Story 1.7.
- **type: schema** — Added `protocol::rest::SessionDetail` (`source`, `session_id`, `state`, `updated_at`) — body shape for `GET /sessions/{id}` responses. Story 1.7.
- **type: schema** — Added `protocol::rest::DaemonStatus` (`daemon_version`, `protocol_version`, `started_at_ms`, `uptime_ms`, `last_event_at_ms`, `last_event_id`) — body shape for `GET /status` responses. `connected_ws_clients` is deferred to Story 3.2 alongside the `bowerbird status` CLI (its first V1 consumer). Epic 2 shipped the semaphore infrastructure (`AppState::ws_semaphore`); only the `DaemonStatus` surfacing was deferred. Story 1.7.
- **type: behavioral** — `GET /sessions`, `GET /sessions/{id}`, `GET /sessions/{id}/events?since=<cursor>`, `GET /sessions/{id}/stats`, `GET /status` are now live. All five require a bearer token via `Authorization: Bearer <token>`. `GET /healthz` and `GET /readyz` remain unauthenticated. Story 1.7.
- **type: behavioral** — `GET /readyz` now also probes the database (`SELECT 1 FROM events WHERE 1=0` against the reader pool). A 200 implies both `migrations_complete` AND `db_probe_ok`; previously only the migrations branch was checked. Story 1.7, AC #2. Resolves the deferred-work item from the Story 1.2 review.
- **type: behavioral** — Bearer-token resolution chain for v1.x is `BOWERBIRD_TOKEN env → generated UUID4 (WARN-logged)`. The full `keychain → env → file` chain documented in `architecture.md:442` is reserved for Story 3.3. The validation layer (`api::auth::require_bearer`, `BearerToken::verify`) does not change between v1.7 and 3.3 — only the issuance source. (`Resolves-In: 3.3`) (Resolved in the Story 3.3 entry below.)
- **type: behavioral** — Ingest socket: `hook_kind` is now required. Story 1.8. The daemon previously accepted ingest lines without a `hook_kind` field and silently treated them as `PreToolUse`. As of this release, a missing or non-string `hook_kind` is rejected with `400 missing hook_kind\n` and any `hook_kind` not in the adapter's known set is rejected with `400 unknown hook_kind: <value>\n` (the `<value>` is the offending string sanitized via `sanitize_for_wire`). The wire JSON schema is unchanged; only the daemon's tolerance for malformed input tightened. Tools that only consume the daemon's outbound surface (REST, WS) are unaffected. The shim already injects `hook_kind` on every payload (Story 1.5) — no shim-side changes required. Resolves the deferred-work item from the Story 1.4 review.
- **type: schema** — **WebSocket surface live at `GET /ws`** (Story 2.1). Authenticated via bearer token in `Authorization: Bearer <token>` header (preferred) or `?token=<token>` query parameter (fallback for clients that cannot set headers, e.g. browser `new WebSocket()`). When the `Authorization` header is present (any value, including malformed), it wins — the query token is NOT consulted as a fallback. On upgrade, the daemon sends one `hello` `ServerMessage` containing `protocol_version`, `daemon_version`, `oldest_available_event_id`, `daemon_started_at`, and `history_begins_cleanly`. Inbound `ClientMessage` uses strict `deny_unknown_fields`: `{"op":"subscribe","topic":...}` and `{"op":"unsubscribe","topic":...}` are the only valid shapes (single topic per message). Supported topics are `events.*`, `events.<source>.*`, `events.<source>.<session_id>`, `state.session.*`, `state.session.<id>`, `state.session.<id>.current_state`. Unknown topics, empty topics, unknown ops, extra fields, binary frames, and non-JSON payloads close the connection with WS close code 1008 (Policy Violation) and a `bad message: ...` reason (sanitized, capped at 123 bytes per RFC 6455 §5.5.1). Outbound `ServerMessage` adds a `State(StateFrame { source, session_id, state })` variant. To make new variants additive across v1.x in practice — not just on paper — `ServerMessage` now carries a `#[serde(other)] Unknown` catch-all on deserialize; older clients (or third-party bindings) using this crate at an earlier version decode future variants as `Unknown` instead of failing on the tag. The asymmetric `deny_unknown_fields` policy alone only covers struct fields, not enum variants; this catch-all closes the gap. Concurrent connection cap is 256 (configurable via `Config::ws_max_connections`); over-cap upgrades return HTTP 503 without upgrading. Idle ping interval is 30s, pong timeout is 10s; on pong timeout the connection closes (deadline-granularity, not next-tick-granularity). Story 2.1 introduced the WS surface and topic grammar; the broadcast-hub publish path was wired into `projection::session::write` by Story 2.2 (see the behavioral entry below).
- **type: behavioral** — **HTTP surface now emits `x-request-id` and respects a 30s per-request timeout and a 1 MiB request-body limit** (Story 2.1). Every HTTP request (including WS upgrade requests up to the point of upgrade) receives an `x-request-id` UUID4 header on the response, propagated for cross-cut tracing. HTTP request handlers (NOT WebSocket connections once upgraded) are bounded by a 30-second wall-clock timeout; requests exceeding it receive HTTP `408 Request Timeout`. Request bodies larger than 1 MiB receive `413 Payload Too Large` from the underlying `RequestBodyLimit` layer. WebSocket connections, once the upgrade is complete, are exempt from both. Existing clients that completed all v1.0 requests in under 30s and stayed under 1 MiB are unaffected. Resolves the deferred-work entry from the Story 1.7 review.
- **type: behavioral** — **`event` and `state` `ServerMessage` frames are now broadcast to WS subscribers** (Story 2.2). Every successful `projection::session::write` (the ingest path's single canonical publisher for non-sentinel events) publishes one `BroadcastEnvelope::Event` followed by one `BroadcastEnvelope::State` after the SQLite transaction commits. WS subscribers to `events.*`, `events.<source>.*`, `events.<source>.<session_id>`, `state.session.*`, `state.session.<id>`, and `state.session.<id>.current_state` (all topics shipped in 2.1) now receive live frames; previously these topics accepted subscriptions but never delivered. Sentinel events with `source = "__daemon__"` (`RecordingStarted`, `RecordingEnded`) are NOT published — daemon lifecycle stays off the user-facing surface. Publishing is gated on `tx.commit()` success: a write that fails to commit produces zero broadcast envelopes. Multiple subscribers are fully independent — closing one WS connection does not affect frame delivery to other subscribers, and the closed connection's semaphore permit is released. End-to-end latency targets hook→presenter p99 ≤100ms (NFR2); not a hard contract-test gate in this release, will be benchmarked separately.
- **type: behavioral** — **WebSocket `state.*` subscriptions now receive a snapshot of matching session projections on subscribe** (Story 2.3). A `Subscribe` for `state.session.*`, `state.session.<id>`, or `state.session.<id>.current_state` causes the daemon to read `session_projections` (sentinel-excluded, ordered `updated_at DESC, source ASC, session_id ASC`) and emit one `ServerMessage::State` frame per matching session BEFORE any subsequent live frame. Frames apply the read-time stale-Working → Idle fallback (`current_state_for_read`) just like `GET /sessions` and `GET /sessions/{id}`. Snapshots are deduped against the pre-existing subscription set on the same connection: subscribing to `state.session.*` then `state.session.<id>` emits zero additional snapshot frames for that id (the wildcard already covered it). Subscriptions to `events.*`-family topics emit ZERO snapshot frames — event history is fetched via REST `GET /sessions/:id/events?since=0` (Story 1.7), not via WS replay. New sessions that appear after subscribe-time still arrive as live `State` frames via Story 2.2's publish path (no reconnect, no re-subscribe, no daemon-side bookkeeping). Snapshot frames are sent directly on the requesting connection's socket, never through the broadcast hub, so other subscribers are unaffected.
- **type: schema** — `SyncFrame::new(oldest_available_event_id, latest_event_id) -> Result<Self, Error>` constructor added (Story 2.3, fold-in from the Epic 1 retro). Rejects `oldest > latest` at construction time with `Error::InvalidSyncFrameOrdering { oldest, latest }`. The serde shape of `SyncFrame` is unchanged — wire payloads (including ones from a hypothetical buggy peer with inverted IDs) continue to round-trip through `Deserialize` without validation. The asymmetric inbound/outbound policy is preserved: tighten outbound construction, leave inbound parsing permissive. No Story 2.3 producer activates the constructor yet; Story 2.4's lagged-consumer recovery is the likely first call site.
- **type: behavioral** — **Lagged WS consumers now receive a `dropped` `ServerMessage` frame** instead of silent skip (Story 2.4). When a per-connection broadcast receiver falls more than `ws_broadcast_capacity` positions behind the publisher, the daemon emits one `DroppedFrame { count, first_dropped_event_id, last_dropped_event_id }` to that socket; `count` is in **envelopes** (not bytes); `first_dropped_event_id` and `last_dropped_event_id` are best-estimate upper-bound values (the broadcast channel does not expose the post-lag cursor synchronously). Presenters MUST recover via REST `GET /sessions/{id}/events?since=<last_delivered_event_id>` where `last_delivered_event_id` is the cursor the presenter authoritatively tracked from prior `event` frames it received — NOT the ids inside the `dropped` frame. Gap-recoverability is the presenter's derivation: `oldest_available_event_id <= last_delivered_event_id + 1`. Lag bursts are coalesced over a sliding `coalesce_window` (default 1s, configurable via `Config::ws_broadcast_coalesce_window`); sustained lag emits a bounded number of `dropped` frames per window, not one per `Lagged` recv. Both the main `rx.recv()` arm and the Subscribe/Unsubscribe drain path route through the same coalescing helper. The socket stays open after `dropped` emission per AC #1, and `last_delivered_event_id` continues to advance on subsequent Event frames.
- **type: schema** — `DroppedFrame::new(count, first_dropped_event_id, last_dropped_event_id) -> Result<Self, Error>` constructor added (Story 2.4, fold-in from the Epic 1 retro / deferred-work.md:9). Rejects `count == 0` and `first > last` at construction time with `Error::InvalidDroppedFrame { count, first, last }`. `DroppedFrame` is now `#[non_exhaustive]` to block struct-literal construction from outside the `protocol` crate; daemon producers must route through `new`. The serde shape is unchanged — wire payloads continue to round-trip through `Deserialize` without validation. Asymmetric inbound/outbound policy preserved, mirroring `SyncFrame::new` (Story 2.3).
- **type: behavioral** — Graceful daemon shutdown now sends each connected WebSocket client a protocol `close` `ServerMessage` with `reason = "daemon shutdown"` before the WebSocket control close (Story 2.5). SIGTERM and SIGINT share the same path: stop accepting HTTP/WS upgrades and ingest connections, drain accepted ingest writes, drain each subscribed connection's broadcast backlog, emit the protocol close, wait up to 5 seconds for WS tasks, then commit the daemon lifecycle sentinel and checkpoint the WAL. `RecordingEnded` remains a database lifecycle sentinel only and is not broadcast to user-facing WS clients. No schema change: `ServerMessage::Close(CloseFrame)` already existed.
- **type: behavioral** — Daemon lifecycle CLI surface (Story 3.2). Two additive protocol-crate changes consumed by the new `bowerbird start` / `bowerbird status` subcommands, both landed in the same release. (1) `protocol::ServerInfo { bind_addr: String }` added to `crates/protocol/src/rest.rs` — describes the `~/.bowerbird/server.json` file the daemon now publishes once `listener.local_addr()` resolves the kernel-assigned ephemeral port; the CLI reads this to find the daemon's HTTP surface for `/healthz` and `/status` probes. The file is written atomically (tmp + fsync + rename) with mode `0600` and best-effort deleted on clean shutdown; after an unclean exit the file is left on disk with a possibly-stale `bind_addr`, so the CLI treats it as a hint rather than a liveness proof (the singleton PID + ingest-socket connect probe are the authoritative checks). Story 3.3 will extend `ServerInfo` with a `token` field — the asymmetric `deny_unknown_fields` policy applies per-direction (daemon-controlled outbound emission to a sibling CLI process), so the absence of `deny_unknown_fields` here is deliberate and documented in the type's doc comment. (2) `protocol::DaemonStatus.connected_ws_clients: u32` added as an additive field after `last_event_id`; the value is computed as `ws_max_connections - ws_semaphore.available_permits()` at request time and reflects WebSocket connections that have completed the upgrade past `try_acquire_owned` and not yet released their `OwnedSemaphorePermit`. Because the semaphore read is a momentary snapshot — not snapshot-consistent across calls — the field is intentionally documented as a count-at-a-point-in-time, not a high-precision metric. v1.0 presenters continue to deserialize `DaemonStatus` responses without modification (the outbound types are permissive on extra fields per the asymmetric serde policy; additive fields are silently ignored by older bindings). Closes Epic 2 retrospective AI-1 / Story 1.7 deferred-work entry for `/status.connected_ws_clients`.
- **type: behavioral** — Bearer-token resolution chain extended (Story 3.3). The daemon now resolves its bearer token in this order: (1) `BOWERBIRD_TOKEN` env var, (2) system keychain via the `keyring` v3 crate (`service = "bowerbird-daemon"`, `user = "bearer-token"`; macOS Keychain on Darwin, Secret Service via D-Bus on Linux), generating and storing a UUID4 on first run if the entry is empty, (3) `~/.bowerbird/config.toml` `token` field (mode 0600 expected; warning on wider mode but value still used). When all three fail, the daemon exits non-zero with a human-readable error to stderr enumerating each tried path (NFR13). The validation layer (`api::auth::require_bearer`, `BearerToken::verify`) and the on-wire `Authorization: Bearer <token>` header format are unchanged — v1.0 presenters continue to authenticate identically. The previous behavioral entry for Story 1.7's `env → generated UUID4` chain is now superseded by this full chain; tools that relied on the auto-generated fallback continue to work (the keychain write-and-persist fills the same role with persistence). New CLI surface: `bowerbird auth token` prints the resolved bearer token to stdout (followed by `\n`, no banner, no prefix; pipe-safe into `Authorization: Bearer $(bowerbird auth token)`). The `bowerbird status` CLI now auto-resolves the token via the same chain — the user no longer needs to set `$BOWERBIRD_TOKEN` to read `/status` details, redeeming the Story 3.2 `"or wait for Story 3.3"` placeholders. A test-only `BOWERBIRD_KEYRING_BACKEND={default|disable|mock}` env override exists for hermetic test runs; the `mock` value is feature-gated behind the daemon's `mock-keyring` cargo feature (defaulted ON for `cargo test --workspace`; release distributions can build with `--no-default-features` so a malicious env-var injection cannot neutralize keychain protection). The CLI mirrors the daemon's chain (env → keychain → config.toml) and does NOT depend on `crates/daemon` (CLI stays tokio-free; the keychain service+user constants are duplicated with cross-pointer doc comments). (`Resolves: 3.3`)
- **type: behavioral** — `protocol::SHIM_BINARY_NAME` value changed from `"bowerbird"` to `"bowerbird-shim"` (Story 3.1, Task 5, Approach B). The constant's identifier stays the same; only the string value it holds changes. This reconciles the constant with the actual hot-path binary name declared in `crates/shim/Cargo.toml` (`[[bin]] name = "bowerbird-shim"`) and frees the unadorned `bowerbird` name for the user-facing CLI binary (top-level `Cargo.toml` `[[bin]] name = "bowerbird"`) introduced by `bowerbird install` / `bowerbird uninstall` in the same story. `bowerbird install` writes the hook command `bowerbird-shim --hook-kind <kind>` into `~/.claude/settings.json` under each known hook kind. The shim source code, its `release-shim` profile, and the Story 1.5 p99 ≤5ms hot-path budget are unchanged — only the protocol constant value rotated to match the binary's actual name. Presenters that read `SHIM_BINARY_NAME` from the protocol crate at runtime see the new value automatically; presenters that hard-coded `"bowerbird"` as a path component need to update to `"bowerbird-shim"`.
- **type: behavioral** — Prebuilt binary distribution shipped (Story 3.4). GitHub Releases now attach three prebuilt tarballs per tag: `bowerbird-vX.Y.Z-aarch64-apple-darwin.tar.gz` (macOS arm64), `bowerbird-vX.Y.Z-x86_64-apple-darwin.tar.gz` (macOS x86_64; cross-compiled from arm64 runner via `rustup target add x86_64-apple-darwin`), and `bowerbird-vX.Y.Z-x86_64-unknown-linux-gnu.tar.gz` (Linux x86_64, glibc 2.35+ — pinned to `ubuntu-22.04` runner so the Linux baseline covers Ubuntu 22.04/24.04, Debian 12+, RHEL 9.0+). Each tarball contains the three binaries (`bowerbird`, `bowerbird-shim` built under the `release-shim` profile for the perf budget, `bowerbird-daemon`), the bundled `tool-reactions.toml` data file under `adapters/claude/`, MIT+Apache-2.0 license files (workspace now dual-licensed per Rust ecosystem convention), the project `README.md`, and `INSTALL.md` with the post-extract walkthrough. SHA-256 checksums are attached alongside each tarball. The release pipeline at `.github/workflows/release.yml` triggers on `v*.*.*` tag pushes or via `workflow_dispatch`; the release-notes template names the artifacts and restates the musl-deferral statement verbatim per AC #2. musl Linux is deferred post-V1 (NFR9); the alternative install path is `cargo install --git https://github.com/<owner>/bowerbird --tag vX.Y.Z` from a stable Rust toolchain (NFR10; no nightly required; `Cargo.lock` committed; `--locked` enforced in CI). Crates.io publishing is also deferred post-V1 — V1 distribution is GitHub-Releases-only (prebuilt) plus git-clone (source). The `bowerbird install` command's hook entry uses the PATH-relative binary name `bowerbird-shim --hook-kind <KIND>` (Story 3.1 AC #1 / Story 3.4 AC #4; pinned by `installed_command_uses_path_relative_binary_name_no_slash_in_first_token` regression test in `crates/adapter-claude/tests/contract_install.rs`) so users who re-download to a different `$PATH` location are picked up automatically without re-running `bowerbird install`. The CI workflow (`.github/workflows/ci.yml`) now serializes the workspace test suite with `cargo test --workspace -- --test-threads=1` per Epic 2 retro AI-3 (Discovery #3) — the daemon contract suite and CLI E2E suites share process-wide state (subprocesses, signal handlers, `BOWERBIRD_DATA_DIR`, `BOWERBIRD_KEYRING_BACKEND`) and parallel execution caused hangs in Stories 1.6, 2.5, 3.1, 3.2, 3.3. The architecture.md WebSocket subsystem section now documents the six runtime config knobs (`ws_max_connections`, `ws_ping_interval`, `ws_pong_timeout`, `ws_broadcast_capacity`, `shutdown_drain_timeout`, `ws_broadcast_coalesce_window`) with defaults sourced verbatim from `crates/daemon/src/config.rs::Config::with_bowerbird_dir` (Epic 2 retro AI-2 / Discovery #2). No wire-protocol surface changes. (`Resolves: 3.4`)
