[`crates/daemon/src/projection/session.rs::WritePrecondition`, `crates/daemon/src/projection/liveness.rs::probe_once`]

## Deferred from: code review of 5-7-session-cwd-on-the-wire (2026-06-02)

1. **Protocol-crate Rust source compatibility policy is undefined for public structs.** Story 5.7 adds required public fields to public Rust structs (`EventEnvelope.cwd`, `Event.cwd`, `SessionState.cwd`, `SessionState.started_at`, `SessionListItem.cwd`, `SessionListItem.started_at`). The Story 5.7 compatibility tests correctly cover the hard project guarantee: REST/WS wire compatibility, where older presenters compiled against older shapes deserialize newer daemon JSON and silently ignore additive fields. They do not make source compatibility true for a Rust consumer that upgrades the `protocol` crate and constructs these structs with literals; that code will fail to compile. This is not unique to Story 5.7 (`last_pid` / `pid` additions used the same pattern), and the project currently documents the hard guarantee as REST/WS wire compatibility within v1.x. A future protocol-crate policy pass should decide whether Rust API source compatibility is explicitly out of scope, or whether outbound structs need constructors/builders/`#[non_exhaustive]`/defaulting patterns before the crate is treated as a stable SDK surface. [`crates/protocol/src/event.rs`, `crates/protocol/src/state.rs`, `crates/protocol/src/rest.rs`]

## Deferred from: correct-course of Story 5.7 — migration-era projection backfills at release time (2026-06-02)

1. **A real migration-era backfill strategy is needed once bowerbird ships a release whose databases must survive upgrades.** Story 5.7 added `started_at` as a *projection-only* field (derived, no `events` column, no migration). For databases written before the field existed, a row reads `null` until rebuilt. While bowerbird is pre-release this is a non-issue: the supported upgrade path on any schema/projection change is "remove `~/.bowerbird/bower.db` and restart," so no legacy rows persist (correct-course 2026-06-02, ADR 0006 Option D — the on-the-fly event-log backfill the four Story 5.7 review passes kept patching was removed because it served only this transitional case). **That changes at the first release that promises durable databases across upgrades.** At that point bowerbird needs a deliberate strategy for fields added to the projection *after* rows already exist — and `started_at` will not be the only one (any future daemon-derived projection field, e.g. a process-birth marker, a per-session counter, or a reclassified `current_state`, has the same shape). Options analyzed in `docs/bmad/planning-artifacts/started-at-backfill-reconsideration-2026-06-02.md`: (a) a one-shot startup backfill pass that recomputes affected projection fields from the event log for pre-existing rows (the honest "rebuild touched rows once" approach — distinct from the per-write on-the-fly backfill that was removed); (b) preserve-`None`/`null` and document the gap; (c) bump a projection-schema version and force a full `rebuild_missing_projections` of stale rows on upgrade. The byte-identical-rebuild contract (`project-context.md` §"Required contract tests" → *Projection rebuild from event log*) is the constraint any choice must respect. This should be decided as part of the release-readiness epic (currently Story 5.14, crates.io + v0.1.0 tag), with its own ADR. [`crates/daemon/src/projection/session.rs::rebuild_missing_projections`, `crates/daemon/src/projection/state.rs::transition`, `crates/protocol/src/state.rs::SessionState`]
