## What shipped

The full user-facing CLI surface plus prebuilt-binary distribution:

- **`crates/daemon/src/singleton.rs`** — `flock(LOCK_EX | LOCK_NB)`-backed singleton lock on `<data_dir>/bowerbird.pid`, acquired before `init_pools` so two daemons can never race SQLite migrations on the same `bower.db`. Kernel reclaims the FD on any exit path (clean, panic, SIGKILL); stale-PID safety probes via `kill(pid, 0)` with a single retry. Closes the Story 1.2 deferred-work entry.
- **`crates/daemon/src/server_file.rs`** — atomic writer for `~/.bowerbird/server.json` (mode 0600, tmp+fsync+rename). Publishes the ephemeral bind-addr so the CLI can find the daemon's HTTP surface without parsing logs. Best-effort unlink on clean shutdown; the file is a hint, not a liveness proof (PID + ingest-socket probe is authoritative).
- **`crates/daemon/src/config_file.rs`** — strict (`deny_unknown_fields`) reader for `~/.bowerbird/config.toml` with `ConfigFile { token: Option<String> }`. Mode-0600 enforcement is operator-friendly (warn but still load) so users on shared boxes can still run the daemon.
- **`crates/daemon/src/api/token.rs`** — extended `load_or_generate` to a four-step chain (`env → keychain → config.toml → Err(TokenError)`) returning `Result<(BearerToken, TokenSource), TokenError>`. `TokenSource` gained `Keychain { generated: bool }` and `ConfigFile` variants (the old `Generated` variant folded into `Keychain { generated: true }`). The validation layer (`require_bearer`, `BearerToken::verify` with `subtle::ConstantTimeEq`) stayed identical, as Story 1.7 predicted.
- **`src/main.rs` + `src/commands/`** — eight new CLI subcommands wired through `clap` derive: `install`, `uninstall`, `start`, `stop`, `status`, `auth token` (alphabetical surface). `src/commands/daemon.rs` is the single source of truth for the shared helpers (`start_daemon_detached`, `stop_daemon_via_pid_file`, hand-rolled HTTP probes, `setsid`-based detached spawn). The CLI binary stays tokio-free and axum-free — verified by `cargo tree -p bowerbird --depth 8 | grep -E 'tokio|axum' = 0` in every story's debug log.
- **`crates/adapter-claude/src/install.rs`** — atomic settings.json install/uninstall (read → parse → merge → write tmp → fsync → rename) with 5-attempt exponential-backoff retry on concurrent-write conflicts. Detects external writes via (inode, mtime, size) baseline. Process-local `AtomicU64` counter in `tmp_path_for` avoids the `SystemTime`-resolution tmp-collision discovered in Story 3.1's dev log.
- **`crates/protocol/src/rest.rs`** — additive `connected_ws_clients: u32` on `DaemonStatus` (closes Epic 2 retro AI-1) plus `ServerInfo { bind_addr: String }` for the new server.json publication. ## What was hard

### The AC-vs-shipped reconciliation in Story 3.3 token chain (Task 1.1 / 1.2)

**What happened:** AC #2 reads literally "Given the keychain is unavailable... falls back in order: (1) env var, (2) config.toml." The shipped order puts env-var FIRST, before the keychain step. Documented in `crates/daemon/src/api/token.rs`'s module doc comment with a three-bullet rationale.

**Why the shipped order is right:**
1. **Test infrastructure reuse.** `tests/cli_lifecycle.rs` shares a known token value between daemon and CLI via `BOWERBIRD_TOKEN`. Putting env-var as the first check preserves that pattern; otherwise every lifecycle test would need keychain mocking and an inter-subprocess mock-state-sharing mechanism the `keyring` crate doesn't support.
2. **Escape-hatch ergonomics.** Users wanting to override a stuck/wrong keychain entry (no rotate CLI in V1) reach for `BOWERBIRD_TOKEN=<...> bowerbird start`. With env-var first, this works without "delete the keychain entry first" pre-step. Env-only-as-fallback would require manual `security delete-generic-password` / `secret-tool delete`.
3. **architecture.md:442 narration reading.** The arrow chain "system keychain primary → BOWERBIRD_TOKEN env-var → ~/.bowerbird/token file mode 0600" reads naturally as "primary, then first override, then second override" — not "primary, with overrides only when primary is unavailable."

**Generalizable lesson:** **The AC's literal text is a starting point, not the contract.** When the implementation discovers a stronger or safer ordering, document the reconciliation inline (module doc comment + `Why env-var wins over keychain` section in the dev notes), preserve the AC's wording in the story file as historical evidence, and let the code be authoritative. The reconciliation discipline keeps the AC honest as a planning artifact without forcing the implementation into a worse design. The Story 3.3 author considered amending the AC text but decided against it — the AC reads what it reads at story-creation time; the *delta from literal AC* is the interesting signal a future reader (or retro author) needs to see.

### Mock-keyring's per-`Entry::new` semantics broke the round-trip test design (Story 3.3 Task 6.3 / 6.9)

**What happened:** Task 6.3 (`keychain_first_run_generates_and_stores`) and Task 6.9 (`keychain_value_preserved_across_two_load_or_generate_calls`) both asked for in-process generate-and-store-then-read-back-same-value coverage of the keychain step. The implementation used `keyring::set_default_credential_builder(keyring::mock::default_credential_builder())` to install a mock backend at startup. But `keyring` v3's mock builder returns a fresh password-less `MockCredential` on every `Entry::new(service, user)` call — no service+user interning. The second `load_or_generate` call gets a fresh mock, not the previously-stored value.

**The fix:** Task 6.3 + 6.9 were merged into `mock_keychain_first_run_generates_and_tags_source` which only asserts the generate branch. The "two calls match" guarantee (NFR14: no hot reload) was preserved by moving the persistence test to a different layer — `tests/cli_auth.rs::status_shows_full_block_without_user_supplied_token` exercises a real cross-process round trip via `config.toml` as the shared persistent backing store (with `BOWERBIRD_KEYRING_BACKEND=disable` to skip the keychain entirely).

**Generalizable lesson:** **Test fakes have their own semantics; don't assume parity with the real backend.** The mock-builder pattern works for "did we attempt the keychain interaction?" but not for "do two attempts see the same value?" The right move is to identify which AC-coverage shape the fake supports and which it doesn't, then route the round-trip coverage through a different layer (here: a real config.toml file shared across two subprocesses). The store-and-recall guarantee for the *real* macOS Keychain / Secret Service backends is exercised by manual smoke at release time; no automated test could reasonably exercise the user's actual platform keychain without polluting it.

### Doc-drift in main.rs from a parallel grep pattern (Story 3.3 review M1)

**What happened:** Story 3.3 Task 9.5 trimmed obsolete "Story 3.3 will extend `ServerInfo` with a `token` field" hints from `crates/daemon/src/server_file.rs:14-17` and `crates/protocol/src/rest.rs::ServerInfo` doc comment. The verification grep used `grep -rn "wait for Story 3.3" src/ crates/` (because two of the obsolete strings were "...or wait for Story 3.3..."). One *additional* obsolete comment lived in `crates/daemon/src/main.rs:248-251` and read "Story 3.3 will fold the bearer token into the same file." The `wait for Story 3.3` pattern didn't match the `Story 3.3 will fold` variant.

**The fix:** Senior review surfaced the missed comment, fixed inline, and the post-review verification grep was widened to `grep -nE "wait for Story 3\.3|Story 3\.3 will"`. The broader pattern is now standard in subsequent stories' verification blocks.

**Generalizable lesson:** **Doc-drift greps that scan for one phrasing miss the others.** A "Story X.Y will <verb>" comment can take many forms: "...will extend...", "...will fold...", "...will replace...", "...wait for Story X.Y...". When designing a doc-drift verification step, write the grep pattern to match the *kind* of comment, not the exact wording. Or — the strictly better option that Story 3.4 demonstrated — write the verification as a compiled Rust test (`tests/release_pipeline_docs.rs`) that walks the actual files and asserts the desired absence/presence with named test functions. Compiled tests can't drift from their own grep pattern.

### File List vs git divergence (Story 3.3 and 3.4 reviews)

**What happened:** Story 3.3's File List omitted `src/commands/start.rs` and `tests/cli_install.rs` (both rustfmt-only reflows from running `cargo fmt --all` after the resolver edits). Story 3.4's File List omitted `tests/release_pipeline_docs.rs` (356 lines of doc-drift guardrail tests) and `scripts/tarball-smoke-test.sh` (186 lines of local pre-tag smoke). In both cases the senior review auto-fixed by reading `git status` and appending the missing files with full descriptions.

**Why it kept happening:** The Dev Agent Record's File List is authored from the dev's memory of intentional edits. Files that get touched as side effects (rustfmt reflow; doc-drift guardrails added mid-story; helper scripts added for local verification) are easy to forget. The Dev Notes "Files this story does NOT touch" list ALSO went stale in both reviews — Story 3.3 claimed not to touch `tests/cli_install.rs` (but did, via rustfmt); Story 3.4 claimed no new test files (but added `tests/release_pipeline_docs.rs`) and no new scripts (but added `scripts/tarball-smoke-test.sh`).

**Generalizable lesson:** **`git status` is the authoritative File List source, not the dev's recollection.** The review pattern that worked: run `git status --porcelain` at review time, cross-reference against the Dev Agent Record's File List, surface the delta as a HIGH finding, auto-fix by appending the missing files. The Story-automator review workflow's File-vs-git audit is the load-bearing check; without it the stories' "File List" sections become unreliable artifacts. A future hardening pass could automate the audit (a `bmad-checkpoint-preview` or `bmad-eval-runner` step that diffs `git status` against the File List), but the current manual review-time check is sufficient at solo-developer scale.

### The pre-existing SQLite-teardown deadlock keeps being skipped (Stories 3.2, 3.3, 3.4)

**What happened:** Story 3.2's verification used `cargo test --workspace -- --test-threads=1 --skip state_plus_event_atomicity_under_sigkill_during_load` after the test name surfaced as a deadlock under serial execution. The skip was carried forward verbatim in Stories 3.3 and 3.4. The Story 3.2 dev log records the rationale: "pre-existing SQLite-teardown deadlock unrelated to Story 3.2, tracked in taskwarrior task `a2ea3bfb` (project:bowerbird +bug) for a real fix."

**Why it's not blocking but is technical debt:** The skipped test is a regression guard for "state + event atomicity under SIGKILL during load." Skipping it for three consecutive stories means three stories shipped without that specific coverage; if a regression landed in one of them, the skip would have masked it. Mitigating factor: none of Stories 3.2/3.3/3.4 touched the SQLite write path, projection step, or signal-handler code that the skipped test exercises — the risk surface is low.

**Generalizable lesson:** **A pre-existing skipped test is a liability that compounds quietly with every story that inherits the skip.** Taskwarrior `a2ea3bfb` is the right tracking primitive (it's a stable UUID; integer task IDs would have drifted), but the test should not stay skipped indefinitely. Recommendation in this retrospective's action items: Story 4.x should prioritize the actual fix (the deadlock is in test teardown, not production code; the symptom is `tokio::runtime` shutdown ordering against the `deadpool-sqlite` pool's `close()` call). Until then, every new story's verification block should `grep -n state_plus_event_atomicity` against its own touched files to confirm it doesn't touch the deadlock-relevant surface.

## Key insights

1. **Sub-decisions deserve explicit three-option analysis when the obvious answer has a hidden cost.** Story 3.1 Task 5 (naming reconciliation) and Story 3.2 Task 2.4 (`ServerInfo` placement) and Story 3.3 Task 2.1 (keyring features) all followed the same pattern: lay out 2-3 approaches with pros/cons, pick one with documented rationale, capture the rejected approaches in the story file as historical evidence. The pattern matters because the next reader needs to know *why* the obvious choice was rejected, not just that it was. Story 3.4's release.yml two-cargo-invocation pattern (workspace-minus-shim under `release`, shim-alone under `release-shim`) is another example — the obvious "one cargo invocation builds everything" would have lost the shim's release-shim profile, and the dev notes capture exactly why.

2. **Doc-drift guardrails as compiled tests beat doc-drift guardrails as greps.** Story 3.3's grep miss (`wait for Story 3.3` vs `Story 3.3 will fold`) was a one-line oversight that a wider regex would have caught. Story 3.4's `tests/release_pipeline_docs.rs` is a 356-line compiled test that asserts the architecture.md table matches source defaults, the AC #5 walkthrough markers appear in both README and INSTALL, the license metadata is present in all five Cargo.toml files. The compiled test can't drift from its own intent — if the assertion fails, the test fails. The grep can drift from its own intent — if the assertion is "the doc and code agree," the grep needs to encode that intent precisely, and a typo in the grep pattern is silent. The retrospective recommendation: any future story that introduces an invariant the dev wants to verify across multiple files should consider whether the verification can be a compiled test rather than a verification-block grep.

3. **The CLI's "no tokio, no axum" invariant is structural protection, not just preference.** Adding tokio to the CLI binary would: (a) bloat the binary size (the CLI is meant to be `< 5MB` per implicit goal, even though no AC pins this), (b) introduce a second tokio runtime instance per process if the user runs `bowerbird start` (the daemon's `tokio::main(flavor = "current_thread")` is sibling-process; a tokio inside the CLI would not collide, but it would still be wasted), (c) bring in a transitive dep cliff (`mio`, `socket2`, etc.) that the hand-rolled `TcpStream + GET /healthz` path avoids. The `cargo tree -p bowerbird --depth 8 | grep -cE '^.* (tokio|axum) v' = 0` post-add check that every Epic 3 story ran is what catches accidental drift — three stories added new deps (`keyring`, `toml`, `serde_json` for ServerInfo parsing) and three stories verified the invariant held.

4. **One protocol-changelog entry per story keeps the changelog readable.** Stories 3.1 (SHIM_BINARY_NAME), 3.2 (DaemonStatus.connected_ws_clients + ServerInfo combined), 3.3 (full token chain), and 3.4 (prebuilt binary distribution) each landed one entry under v1.0 → v1.1, all `type: behavioral`. The combined Story 3.2 entry covering two related additions (ServerInfo + connected_ws_clients) is the right shape — same release, two related additions, one entry that names both with clear cross-references. The discipline is consistent with Epic 2's "8 new entries under v1.0 → v1.1" pattern; v1.1 of the protocol is now at 12 behavioral + 3 schema entries cumulative across Epics 2 and 3.

5. **Backlinks in deferred-work.md as a closure-record substrate.** `docs/bmad/implementation-artifacts/deferred-work.md` now has 6 strike-through entries with `**Resolved by Story X.Y (Task Z):**` backlinks covering: Story 1.2 singleton → 3.1, Story 1.7 connected_ws_clients → 3.2, Story 1.7 token chain → 3.3. Five new deferred-work entries opened by Story 3.4 (macOS code-signing, `bowerbird install` auto-copy of tool-reactions.toml, crates.io publishing, Windows support, x86_64-apple-darwin runner watch). The ledger is doing what the Epic 1 retro design predicted — discoveries during one story become explicit work tagged to a future story, with backlinks so the closure is searchable. Epic 4 will continue this pattern.

6. **The two-binary user story stays simple.** Users install one CLI (`bowerbird`) and one shim (`bowerbird-shim`). The shim is invisible — Claude Code's hook engine invokes it via a PATH-relative name in `~/.claude/settings.json`. The user types `bowerbird install / start / stop / status / auth token / uninstall`. AC #4 in Story 3.4 (PATH-relative invocation, no slashes in the hook command's first token) is what makes the second-binary invisibility work: a user re-downloading to a different `$PATH` location picks up the newer shim automatically without re-running `bowerbird install`. The `installed_command_uses_path_relative_binary_name_no_slash_in_first_token` regression test pins this invariant against future drift.

## Team agreements (additions to A1/A2/A3/A4/A5/A6 carry-forward)

### A7. Doc-drift verification as a compiled test, not a verification-block grep

When a story introduces a doc-drift hazard (a constant value that must match a documented value; a markdown section that must reflect a source-code default; a multi-file invariant like "this paragraph appears verbatim in three files"), the verification should be a compiled Rust test that walks the files and asserts the invariant, not a one-liner grep in the Dev Notes Verification block.

**Why:** Greps drift from their own intent. Story 3.3's `wait for Story 3.3` grep missed a `Story 3.3 will fold` variant. Story 3.4's `tests/release_pipeline_docs.rs` is the alternative pattern: 356 lines of named test functions, each asserting a specific invariant (`architecture_md_documents_all_six_ws_config_knobs`, `readme_install_walkthrough_covers_a_through_g_markers`, `every_published_crate_declares_mit_or_apache_license`). If the invariant breaks, the test fails — no human grep-pattern maintenance.

**Trigger condition:** the story has more than one place where a documented value must match a code value, OR the story documents an invariant across multiple files (README + INSTALL + a workflow YAML), OR the story introduces a new "Story X.Y will <verb>" comment that needs to be redeemed in a future story.

**How to apply:** add the test file at workspace-root `tests/<story>_drift_guard.rs` (or per-crate `crates/<crate>/tests/`); name each test for the invariant it asserts; anchor file paths at `CARGO_MANIFEST_DIR`-relative paths so the test is hermetic; keep test bodies declarative (read file → string-match assertions) so the failure messages are useful.

### A8. AC-vs-shipped reconciliation lives in the module doc comment

When implementation discovers that a literal AC reading is wrong or suboptimal, the implementation:
1. Ships the right design.
2. Documents the reconciliation in the relevant module's doc comment, naming the AC's literal text AND the shipped order/shape AND the rationale.
3. Does NOT amend the AC in the story file (the AC is historical evidence of what was understood at story-creation time).
4. Notes the delta in the story's Dev Agent Record's Completion Notes so a retrospective reader can find the reconciliation later.

**Why:** AC text is a planning artifact. Implementation discovery is real engineering signal. Amending the AC erases the signal; documenting the reconciliation preserves both the planning intent and the engineering reality. Story 3.3's `crates/daemon/src/api/token.rs` module doc comment is the model — three-bullet rationale, "departure from AC #2's literal text" framing, and the future-reader hook ("can revisit via a new ADR if the AC's literal reading becomes the strict requirement").

**Trigger condition:** the implementation shipped a contract that is *stronger or safer* than the AC's literal text demanded, AND the AC text could be read as forbidding the shipped contract.

### A9. The senior-review File-vs-git audit is load-bearing, not optional

Every `bmad-story-automator-review` pass MUST run `git status --porcelain` and cross-reference against the Dev Agent Record's File List. Files in `git status` not in the File List are HIGH findings; files in the File List not in `git status` are HIGH findings (the dev claimed an edit that didn't ship).

**Why:** Stories 3.3 and 3.4 both had silent File List drift caught only at review time. The drift compounds: downstream tooling (test-summary generators, code-review scopers, retro authors) reads the File List as truth. A wrong File List propagates incorrect coverage claims into the retrospective document.

**Trigger condition:** the review workflow itself (every review). The audit is the senior reviewer's responsibility; it cannot be skipped because the dev claimed the File List is complete.
