## What was hard

### The `Reaction::deserialize` bug had been silently breaking the additive-compat claim since v1.0

**What happened:** The protocol's compatibility guarantee (FR36 / NFR19) reads "tools built against v1.0 continue to work on any v1.x daemon release without modification." Outbound wire surface is supposed to be additive only — new variants land but existing variants stay decodable. Every wire-format snapshot test in `crates/protocol/tests/contract_protocol.rs` had been asserting PascalCase variant names and additive-compat on the *struct* layer (extra unknown fields decode, fields are never removed). But the `Reaction` enum uses a hand-written `Deserialize` impl (not derive), and the final branch of that impl was:

```rust
Err(de::Error::custom(format!("unknown Reaction: {s}")))
```

Meaning if a future v1.x daemon emitted `Reaction::Block` (hypothetical future variant), a v1.0 presenter would FAIL to decode the event entirely — silently breaking the contract the daemon had been making since v1.0. The `#[serde(other)]` attribute that handles this case for derived enums (`ServerMessage::Unknown` is the template) doesn't apply to hand-written `Deserialize` impls.

**The fix:** Change the final branch from `Err(...)` to `Ok(Reaction::Unknown)`. One-line behavioral fix; pinned by `reaction_unknown_variant_round_trips_via_unknown` test and `event-with-unknown-reaction.json` corpus fixture.

**Generalizable lesson:** **Compatibility guarantees that are tested on struct layers but not on enum-variant deserializers are half-tested.** The asymmetric `deny_unknown_fields` policy (strict inbound, permissive outbound) is a struct-level policy; it does nothing for enum variants. A future v1.x will introduce new variants of `Reaction`, `EventKind`, `SessionCurrentState`, possibly `ServerMessage` and others; every wire-surface enum needs a catch-all path (`#[serde(other)] Unknown` for derived enums; a `_ => Ok(Unknown)` arm for hand-written deserializers). The Story 4.4 audit found this because the work was structured as a per-enum walk with explicit "Action + Justification" for each; an ad-hoc grep for `serde(other)` would have missed `Reaction` entirely because it has no derive. The Story 4.4 audit pattern (per-element walk, per-element decision in the doc comment, per-element regression test) is now the structural protection — any future Reaction-shaped surprise will be caught by the same audit shape.

### TypeScript-on-Node ergonomics: WebSocket constructor headers, signal-handler reentrancy

**What happened:** Story 4.2's three examples all need to send `Authorization: Bearer <token>` on the WebSocket handshake. Node's built-in `WebSocket` (undici-backed since Node 22) accepts a `headers` options bag in the constructor; the DOM lib's `WebSocket` type definition does NOT — it's `new WebSocket(url: string | URL)` with no second argument. The TypeScript code path is:

```ts
// @ts-expect-error — DOM lib doesn't know about Node's headers options
const ws = new WebSocket(url, { headers: { Authorization: `Bearer ${token}` } });
```

The `@ts-expect-error` comment is the right shape (the runtime works; the DOM types are wrong for this runtime), but it's a smell that surfaces every time a presenter author types this exact pattern. The fallback (the daemon also accepts `?token=<token>` query parameter from Story 2.1) is documented inline.

Similarly, `reconnect-recovery`'s SIGTERM/SIGINT handler hung in a quiet `await new Promise` (the recovery-completion sentinel) because no reference to the active WS was captured at signal-time. The review fix captured the active WS in module-scope and called `ws.close()` + `setTimeout(process.exit(0), 100)` on signal so Ctrl-C breaks out of the wait instead of hanging.

**Generalizable lesson:** **TypeScript-on-Node is the right choice for the presenter author audience, but the runtime/type-system seam needs explicit documentation.** Every example author who follows the bowerbird path will hit the same `@ts-expect-error` and the same signal-handler reentrancy. Story 4.3's `docs/presenter-authoring.md` documents both patterns inline with the code samples; future cookbook entries should reference them rather than re-document them. ### The "dead code" with a load-bearing `Drop` side-effect

**What happened:** Story 4.4's `crates/daemon/benches/hook_to_presenter.rs` carries a `Daemon { home: TempDir, ... }` struct. The `home` field is never read after construction — but its `Drop` impl is what cleans up the TempDir when the bench exits. The initial dev pass added `use std::sync::Arc;` and `let _ = Arc::new(0u8);` with a comment that literally said "Silence unused warning on Arc + home_guard." The review surfaced this as MEDIUM dead code: the workaround was working around the wrong thing — the real issue was clippy correctly flagging `home: TempDir` as `dead_code`. The fix was to remove the `Arc` workaround entirely and apply `#[allow(dead_code)]` to the `home` field with a comment naming the rationale ("only the Drop side-effect matters; never read at runtime").

**Generalizable lesson:** **A clippy warning about unused code is sometimes correct *AND* the code is load-bearing.** The right answer is `#[allow(dead_code)]` with a doc comment explaining the side-effect, not a sentinel allocation that exists only to make the warning go away. Story 4.4 documented this in the bench file's top-of-file comment; the pattern recurs whenever RAII-style cleanup is the only purpose of a field (TempDir guards, lock guards, MutexGuard wrappers held for their scope). The reviewer caught this because the comment "Silence unused warning" was a red flag — comments that name the workaround instead of the intent are smells. If a comment reads "Silence X" it's worth checking whether the real signal that X was warning about is actually a real issue or genuinely doesn't apply.

## Key insights

1. **The audit-as-walk pattern surfaces silent contract bugs that ad-hoc greps miss.** Story 4.4's per-enum walk (`ServerMessage`, `ClientMessage`, `EventKind`, `Reaction`, `Error`, `SessionCurrentState`) with explicit "Action + Justification" for each found the load-bearing `Reaction::deserialize` bug because the audit was complete, not because the bug was easy to find. The pattern generalizes: when a project claims a property holds across N elements (here, "additive-compat decodes for every wire-surface enum"), the audit needs to walk all N elements explicitly and document the per-element decision in the code, not just trust that "we follow the policy." Story 1.4 review surfaced PRAGMA-on-every-checkout the same way; Story 4.4 surfaces serde(other)-on-every-wire-enum the same way. The shape is: structured walk → per-element evidence → compiled test pinning the per-element decision.

2. **Compiled tests beat greps, now applied three structural ways: doc-drift, cookbook-include, and protocol-changelog gate.** Epic 3 retro introduced the pattern with `tests/release_pipeline_docs.rs`. Story 4.3 generalized it with `tests/cli_docs_drift.rs` covering five different invariants (required docs exist, cookbook entries have canonical four-section shape, cookbook-include directives byte-match example anchors, bidirectional anchor-consumer integrity, README links resolve). Story 4.4 took it further with `tests/protocol_changelog_gate.rs` — a compiled test that walks git refs (or shells out to `git diff`) and asserts the policy holds in the PR diff, not just in the working-tree state. Three different invariant shapes, three different compiled tests, all on the standard `cargo test --workspace` lane. **The pattern is now structural to the project**: any future story that introduces a multi-file invariant should consider whether a compiled test can express it more tightly than a verification-block grep.

3. **The bundled-fixture-as-include_bytes! pattern is a substrate-level discipline, not a Quickstart-specific hack.** Story 4.1's `fixtures/replay-demo.jsonl` is the single source of truth across three consumers: compile-time embed into the `bowerbird` CLI binary (no-arg `bowerbird replay`), runtime read by `bowerbird replay <path>` in Node example smoke tests, runtime read by the daemon's `POST /replay` handler when a user supplies their own JSONL file. ## Significant discoveries

### Discovery #1 — The `Reaction::deserialize` additive-compat bug was a latent contract lie

**What:** The protocol's v1.x compatibility guarantee (FR36 / NFR19) was being asserted on the struct layer but not on the enum-deserializer layer. `Reaction::deserialize` (hand-written, not derive) would have failed to decode any future v1.x reaction string like `"Block"` — silently breaking a contract the daemon had been claiming since v1.0. Story 4.4's per-enum audit found it because the audit was structured, not because the bug was easy to find.

**Impact on V1 release readiness:** The fix is shipped (one-line behavioral change + corpus fixture + regression test). The fix went out as part of v1.x → v1.1 in the protocol changelog under `type: schema` with the four sub-items called out. No production surface; no in-flight presenter authors; the bug is closed before any v1.1 reaction variant ships. **No release-prep action required.**

**Generalizable concern:** The pattern (a struct-level compatibility test that doesn't catch enum-level breakage) is exactly the shape of issue that would have caused a v1.1 release to break v1.0 presenters silently. The Story 4.4 per-enum audit + the wire-format corpus + the contract-test inventory together close this gap structurally. Any future hand-written `Deserialize` impl on a wire-surface enum should be flagged at code-review time for "does this have a catch-all variant?" — the audit's per-enum walk is the procedural protection.

## Team agreements (additions to A1/A2/A3/A4/A5/A6/A7/A8/A9 carry-forward)

### A10. Wire-surface enums get a per-enum audit before any v1.x → v2 promotion

When the protocol's compatibility guarantee is asserted on a wire-surface enum, the enum must have either (a) `#[serde(other)] Unknown` for derived enums, OR (b) a `_ => Ok(Unknown)` arm for hand-written `Deserialize` impls, OR (c) a written justification in the enum's module doc comment explaining why a catch-all variant doesn't apply (the inbound `deny_unknown_fields` pattern for `ClientMessage`; the never-wire-serialized pattern for `Error`). The audit walks every wire-surface enum in `crates/protocol/src/` explicitly — no enum is implicitly "covered" by another enum's catch-all variant.

**Why:** Story 4.4 found the `Reaction::deserialize` bug because the audit walked all enums explicitly. A grep for `serde(other)` would have missed `Reaction` because it has a hand-written `Deserialize`. The audit's value is the structural completeness, not the cleverness of the search pattern.

**Trigger condition:** any future PR that (a) adds a new wire-surface enum to `crates/protocol/src/`, OR (b) changes the `Deserialize` impl of an existing wire-surface enum, OR (c) promotes a protocol version (v1.x → v2). The audit is checked at PR review time; the per-enum justification is updated in the doc comment in the same PR.

**How to apply:** the audit template lives in `docs/protocol.md` §Versioning policy (Story 4.3 authored the policy text; future stories should extend it with the audit table from Story 4.4 AC #6 as a worked example).

### A11. Bundled fixtures use `include_bytes!` for compile-time embed; the in-tree path is the single source of truth

When a story ships a fixture that needs to be available at runtime (Quickstart demos, replay-demo, future v0.1.0 wire-format corpus for cross-version tests), the fixture lives at a single in-tree path (e.g. `fixtures/replay-demo.jsonl`, `tests/fixtures/protocol-v1-corpus/*.json`). Consumers read it via `include_bytes!` (compile-time embed for the CLI binary) or `std::fs::read` (runtime read for test harnesses). The fixture is NEVER duplicated; if two consumers need it in different formats, one consumer transforms at consume-time.

**Why:** Story 4.1's `fixtures/replay-demo.jsonl` is read by three consumers (CLI compile-time embed, daemon `POST /replay` request body parser, Node example smoke test indirectly via `bowerbird replay`). One source, zero version drift, statically-asserted invariants. The pattern generalizes: any future fixture (v0.1.0 wire-format corpus, multi-session-state snapshot, etc.) should follow the same shape.

**Trigger condition:** any story that introduces a new fixture file. The story's task list should explicitly name the fixture's in-tree path and its consumers; the verification block should include a `grep -nE 'include_bytes!\("\.\./\.\./fixtures/'` or equivalent that asserts the path is used, not hard-coded elsewhere.

**How to apply:** the canonical location is `fixtures/` (workspace root) for runtime-shared fixtures, `tests/fixtures/` for test-corpus fixtures. The `architecture.md §Fixture Ownership` table (Story 4.2 Task 6.3 added it) is the authoritative ownership index; new fixtures append a row.

### A12. Manual user-action items get a tracked release pre-flight checklist

When a story's task list includes items the dev workflow cannot execute autonomously (e.g. opening real draft PRs, seeding CI baselines from artifact downloads, manual smoke against a daemon binary that's not on `$PATH`), those items get tracked in a project-level release pre-flight checklist, not just in the story's Deferred follow-up section.

**Why:** Story 4.4 deferred Tasks 4.3 (shim chaos PRs), 7.7 (daemon bench chaos PRs), 3.4 (taskwarrior closure), the daemon-bench baseline seeding, the cross-version upgrade test load-bearing date. Five manual user actions, each tracked in a different Story 4.4 Completion Notes bullet. Without consolidation into a checklist somewhere visible, these items risk slipping past the V1 release tag. The retro's Action Items table is the current consolidation; AI-9 turns it into an in-tree `docs/release-checklist.md`.

**Trigger condition:** any story that defers user-action items the dev workflow cannot complete. The Dev Agent Record's "Deferred to follow-up work / human action items" section is the per-story tracking; the retro's Action Items table is the per-epic consolidation; `docs/release-checklist.md` (AI-9 above) is the cross-epic pre-flight.

**How to apply:** when a story defers a user-action item, name it explicitly in the Dev Agent Record's "Deferred" section, include estimated lift, include a verification criterion. The retro author rolls these into the action items table; the release-checklist author rolls those into the pre-flight checklist before the tag is cut.
