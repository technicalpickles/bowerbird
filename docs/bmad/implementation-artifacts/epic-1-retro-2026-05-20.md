## What shipped

The full agent-activity capture pipeline:

- `crates/protocol` — versioned wire types with strict-inbound / permissive-outbound serde policy
- `crates/shim` — sync hot-path binary, no async runtime, no heap on hot path, per-platform p99 baselines committed
- `crates/daemon` — single-threaded Tokio + axum, WAL-mode SQLite via deadpool, two pools (writer max=1, readers max=4)
- `crates/adapter-claude` — Claude Code hook normalization, TOML reaction config, `(source, session_id)` natural-key
- REST query API — `/healthz`, `/readyz`, `/sessions`, `/sessions/{id}`, `/sessions/{id}/events?since=`, `/sessions/{id}/stats`, `/status`, all bearer-token gated except health/ready
- Atomic state + event persistence under SIGKILL — subprocess crash contract test passes
- Hook unreliability tolerance — projection rebuild on startup converges any orphaned events row

## What was hard

### The wire-framing drift (Stories 1.3 → 1.5 → 1.8)

**What happened:** Story 1.3 shipped against newline-delimited JSON (one `{json}\n` request, one status-line response: `200\n` / `503\n` / `400 <reason>\n`). The PRD (line 365) said `POST /ingest via HTTP/1.1`. The architecture (line 984) said framing was "TBD at implementation time." Story 1.5's author hit the contradiction cold and flagged it.

**How it actually happened (not what it looked like):** This was not accidental drift. The decision was deliberate and documented at story-creation time in `1-3-unix-socket-ingest-endpoint.md:143-163` under a header literally titled "Wire Protocol Decision: Newline-Delimited JSON". Reasoning was recorded in the story file:

> The shim (story 1.5) uses sync I/O only (no Tokio, no HTTP client). Writing bytes to a socket is the simplest sync operation. HTTP headers add ~200 bytes per request and require an HTTP parser, both of which add latency and complexity to the shim's hot path.

The failure was not the decision itself. It was that the resolution lived only in the story file and never propagated back to the upstream artifacts (PRD, architecture) that downstream readers consult first.

**The reasoning was overstated.** On a Unix socket on the same machine, HTTP/1.1 parsing is microseconds, three orders of magnitude under the 5ms p99 budget. The "200 bytes per request" figure is roughly 3× too high for a minimal POST. `httparse` exists exactly for this case (~1500 LOC, zero-copy, no_std). The bytes don't move latency on a loopback socket either.

The real driving force was probably **shim-dep minimalism aesthetic**, not the perf budget. The shim already had hard constraints ("no Tokio, no anyhow, no heap on hot path"). Adding `httparse` even though tiny breaks the *feeling* of a minimal binary. The 5ms budget then gets cited as quantitative justification, but it wasn't binding: there's ~4.9ms of slack.

**The tell:** NDJ's response uses HTTP-shaped status codes (`200`, `503`, `400`) precisely because HTTP's vocabulary is universal. The team didn't actually want to escape HTTP. The team wanted to escape HTTP's *deps*. That's a different motivation worth naming.

**Not worth rewriting.** It works, it's tested, the shim ships. But the principle matters going forward, and the bespoke choice should be narrated honestly in Story 4.4's protocol documentation, not retconned as a perf-driven decision.

## Key insights

1. **The shim is the only bespoke surface in the system.** Everything else reaches for standards: axum (HTTP), tokio-tungstenite (WS, Epic 2), rusqlite + deadpool (DB), serde (JSON), rusqlite_migration, criterion (bench), `subtle::ConstantTimeEq` (auth). The ingest socket is the outlier — worth being clear about why so Epic 2 doesn't inherit the wrong lesson.

2. **`bmad-create-story` resolving a "TBD" is fine. Leaving the resolution only in the story file is the bug.** When an upstream artifact (PRD, architecture) says "TBD at implementation time" and the story-creation pass picks a side, the upstream artifact needs to be back-amended inline as part of that story's creation. Otherwise downstream readers source from a stale doc.

3. **HTTP-shaped status codes on a non-HTTP wire is a coherent hybrid.** Borrow the vocabulary (`200`, `503`, `400`) because it's universal. Drop the protocol because it costs deps. The shim reads exactly one line and checks the prefix. That's not "halfway HTTP"; it's "HTTP-flavored ASCII for the bits that earn their keep, nothing else." Reasonable for a 5ms-budget hot path even if the budget itself wasn't binding.

## Team agreements (carry forward to all future epics)

### A1. Standards-by-default with measured exceptions

Reach for industry-standard protocols and libraries (HTTP, WS, JSON, TLS, etc.) by default. When perf or footprint pressure pushes toward a custom protocol, the deviation must include:

(a) A benchmark showing the standard genuinely fails the budget on reference hardware, and
(b) A paragraph in the relevant ADR or story file explaining why the standard's *deps* were the load-bearing constraint, not just "it'd be faster."

Performance-minded does not mean perf-justified inventing.

### A2. Story-creation back-propagates ambiguity resolutions

When `bmad-create-story` resolves a "TBD" from upstream architecture or PRD, the resolution gets back-amended to the upstream doc inline as part of story creation — not left only in the story file.

**Enforcement:** if a story file contains a new decision header (like 1.3's "Wire Protocol Decision"), confirm the corresponding section in `architecture.md` / `prd.md` has been updated to match before the story is marked `ready-for-dev`. Add to story validation pass.
