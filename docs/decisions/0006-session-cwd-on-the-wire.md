# 0006. Session working directory (and start time) as mechanical facts on the wire

## Context

The wire carries `source`, `session_id`, `current_state`, `last_event_kind`, `last_event_at_ms`, `last_pid`, and the verbatim event payload — but nothing about *where* a session runs or *when* it started.

Two live dogfooding sessions on 2026-06-01 (`docs/dogfooding-feedback.md`) made this concrete. Building the pickletown web `/sessions` page into a triage radar against `bowerbird-deck` surfaced that the first question a multi-session human asks — "which repo or directory is the one waiting on me?" — has no answer on the wire. A presenter cannot group or filter by repo because the daemon never surfaces the cwd (Finding 3). The same gap appears from the labeling side: cards and rows key on the last 8 characters of the `session_id` UUID, with nothing human-recognizable to tell two sessions apart (Finding 4).

Finding 4 brushes against the no-list's "No personas / agent-roles abstraction" cut, and rightly so — a role/persona model is presenter-level interpretation, not a daemon responsibility. The distinction worth recording is narrower: **a presenter can only label by data on the wire, and today there is none a human recognizes.** The intentional cut is the persona model; the missing *raw fact* a label could be built from is not. The working directory is exactly that raw fact.

This is the same test ADR 0004 applied to process liveness. The Axiom 4 question: is `cwd` *a fact the daemon knows*, or *an instruction the presenter would derive*? Claude Code already reports `cwd` on every hook payload (a top-level field alongside `session_id`, `transcript_path`, `hook_event_name`). The daemon observing and carrying that value verbatim is fact-preservation, not interpretation — the same shape as carrying `last_pid`. By contrast, *repo name*, *project*, and *branch* are derivations a presenter computes from `cwd` (resolve the git root, take the last path segment, read `.git/HEAD`); those are presenter concerns and do not belong on the substrate.

Adding a field to the wire protocol is an ADR trigger per `docs/bmad/project-context.md` §"ADR triggers" ("Adds, removes, or modifies the wire protocol"). This ADR records the decision before the field lands.

A sibling ergonomics gap rides along: `started_at`. A presenter rendering "session started 3 minutes ago" today either tracks the earliest `last_event_at_ms` it has personally observed, or makes a side fetch to `GET /sessions/{id}/events?since=0` and reads the first row's `created_at`. Both are awkward on the snapshot-on-subscribe path. `started_at` was deferred from Story 5.3 (deferred-work entry #3) as a future presenter-ergonomics pass; it is bundled into Story 5.7 because it is the same *kind* of fact (a mechanical observation the daemon already has) and the cost of adding it alongside `cwd` is marginal.

## Decision (one sentence)

The daemon carries each session's working directory verbatim as `SessionState.cwd` / `Event.cwd` (a mechanical fact extracted from the source's hook payload, applied with the same overwrite-on-Some carry-forward as `last_pid`) and each session's start time as `SessionState.started_at` (a mechanical fact the daemon derives from the first event it observes); presenters derive repo, project, branch, and age from these facts — the daemon does not.

Specifics:

- **`cwd: Option<String>`** on `SessionState`, the internal `EventEnvelope`, the stored `Event`, and `SessionListItem`. Sourced by the `adapter-claude` `normalize` step reading the native top-level `cwd` from the hook payload (no shim change — the shim already forwards the payload verbatim; a missing or non-string `cwd` yields `None` without failing normalization). Carry-forward / overwrite-on-Some across events (`cwd.or(prev.cwd)`), identical to `last_pid`. Stored in a nullable `events.cwd TEXT` column (schema migration v3) so projection rebuild reads it from a typed column rather than re-parsing source-specific payload shape.
- **`started_at: Option<i64>`** (epoch ms) on `SessionState` and `SessionListItem` only — NOT on `EventEnvelope`/`Event` (it is a session-level projection fact, not a per-event field). Daemon-derived: set once to the first observed event's timestamp and never overwritten (`prev.started_at.or(Some(now_ms))`). No payload field, no adapter code, no `events` column, no migration — it is derivable from the per-event `created_at` already stored, and reconstructs identically on rebuild because the rebuild loop replays events oldest-first.
- **`cwd` is stored verbatim.** No path canonicalization, no `~` expansion, no symlink/`realpath` resolution, no trailing-slash or case normalization. Whatever the source reported is what the daemon stores. Path semantics are OS- and filesystem-specific (APFS case-insensitivity, symlinks, bind mounts); resolving them is a presenter choice, not a substrate responsibility.

## Alternatives considered

- **Shim injects `cwd` like `bowerbird_ppid`.** Rejected: Claude's hook payload already carries `cwd` natively, so a shim inject would add a syscall to the hot path for a value that is already present, and the shim's own cwd would be Claude's cwd anyway. `bowerbird_ppid` is shim-injected only because Claude does not report its own PID; `cwd` has no such gap. Keeping the shim a pure passthrough (it forwards the payload verbatim after inserting only `hook_kind` + `bowerbird_ppid`) is the cheaper and more honest design.
- **Presenter extracts `cwd` from the verbatim `payload` itself.** Rejected: it forces every presenter to know each source's payload shape (Claude puts it at top-level `cwd`; a future Codex/OpenCode adapter may not), and a presenter cannot carry-forward `cwd` across events that lack it without re-implementing the projection. Normalizing it once into a typed field is the substrate's job — the same argument that justified extracting `bowerbird_ppid` into `last_pid` rather than making presenters parse it.
- **Daemon emits a derived `repo` (or `project`, or `branch`) field.** Rejected per Axiom 4. `repo` is an interpretation of `cwd` (resolve the git root); `branch` requires reading `.git/HEAD`; `project` is a naming convention. These are presenter derivations. Emitting them would smuggle "here is what this location means" semantics into a substrate response. The daemon emits the fact (`cwd`); the presenter decides what it means.
- **No `events.cwd` column — re-parse `cwd` from the stored `payload` during rebuild** (the way Story 5.3 re-parses `notification_type` from payload during rebuild). Rejected: a typed column keeps `rebuild_missing_projections` decoupled from source-specific payload shape (it reads one column, not "Claude puts cwd at top-level"), and it mirrors `last_pid` exactly so the codebase has one carry-forward pattern, not two. `notification_type` is re-parsed from payload only because it was a deliberate Story 5.3 scope decision not to give it a column; that is not a precedent to copy for a field whose whole purpose is stable per-session carry-forward.
- **Defer `started_at` to a separate later story.** Considered (it is its own deferred-work item). Rejected for bundling because it is the same kind of mechanical fact, the snapshot-ergonomics motivation is live right now (the same triage-radar build that surfaced `cwd`), and adding it alongside `cwd` is marginal cost — it needs no payload field, no adapter change, no migration. Bundling closes both halves of the "presenters can only triage on what the wire carries" finding in one pass.
- **Read the transcript to build a richer label (e.g. the session's first prompt).** Rejected on Axiom 1 — the substrate observes hook events; it does not interpret message content. The first prompt lives in the transcript, which bowerbird never reads. `cwd` is the label material that *is* a hook fact.

## Consequences

- **Additive, backward-compatible.** Both fields are `Option<T>` on outbound (permissive) types. A v1.0 / pre-5.7 presenter decodes frames carrying `cwd` / `started_at` and silently drops them via the asymmetric `deny_unknown_fields` policy (outbound types are permissive on extra fields). No new error condition, no protocol-version bump within v1.x. One `type: schema` entry in `docs/protocol-changelog.md`.
- **Finding 4 resolves without a persona model.** Presenters can now build a recognizable label (e.g. the last path segment of `cwd`) and group/filter by directory. The no-list persona/agent-roles cut stands — this adds the raw fact, not the interpretation.
- **`cwd` projection carry-forward matches `last_pid` exactly** — overwrite-on-Some, applied in every `transition` arm. A session whose cwd changes mid-session (rare, but Claude's reported cwd can shift) tracks the latest; an event that omits cwd preserves the prior. The first event of a session always carries the initial cwd on the `State` frame (it is a `None → Some(state)` transition).
- **`started_at` is set-once, the inverse direction from `cwd`.** This is the one place in the projection where "prior value wins." It is daemon-derived (no producer cooperation required) and survives rebuild because the event log replays oldest-first. The deliberate asymmetry (cwd overwrites, started_at preserves) is documented in Story 5.7's Dev Notes as an anti-footgun.
- **Legacy projection rows backfill `started_at` from the event log on their next write** (Story 5.7 code review). A session whose projection predates this change deserializes with `started_at: None`, and `rebuild_missing_projections` skips rows that already have a projection — so without intervention the next post-upgrade event's clock would leak into `started_at` (a false "started just now"). The projection write path reads `MIN(events.created_at)` for that `(source, session_id)` when the prior state's `started_at` is `None`, restoring the same value a full rebuild produces. This is what makes "reconstructs identically on rebuild" (above) hold across the *upgrade* boundary, not just for a clean rebuild — the live projection stays equal to a byte-identical rebuild. The query fires only for legacy rows; a post-5.7 session sets `started_at` on its first event and never reaches it. No blob rewrite, no migration — consistent with the no-data-migration consequence below.
- **No retention or growth pressure.** Both fields ride existing rows (`cwd` adds one nullable column; `started_at` adds zero). `cwd` strings are bounded by the shim's 1 MiB payload cap, same trust model as `payload`.
- **Schema migration v3** (`ALTER TABLE events ADD COLUMN cwd TEXT`) is additive and idempotent; pre-v3 rows get `cwd = NULL`. Pre-5.7 projection blobs lacking either field deserialize to `None` (serde defaults absent `Option` fields) — no blob rewrite, no data migration, the same mechanism `last_pid` relied on in Story 5.3.
- **A cwd-only change does not push a `State` frame** for a session whose `current_state` is unchanged, because of Story 5.2's transitions-only broadcast gating. The cwd still reaches presenters on the `events.*` frame, on the next genuine state transition, and on snapshot/REST. This is acceptable: cwd is stable per session and the first event of any session transitions state, carrying the initial cwd. (Surfacing every cwd change as a live state push would mean re-broadcasting state on cwd-only writes — not worth inverting the 5.2 policy for a value that rarely changes.)
- **Cross-source generality is deferred but not foreclosed.** The extraction is currently Claude-specific (`payload.cwd`). A second adapter that reports its working directory under a different key adds its own extraction in its own `normalize`; the protocol field is source-agnostic.

## Revisit when

- A second adapter (Codex, OpenCode, …) reports its working directory under a payload key other than top-level `cwd` — the per-adapter extraction needs a deliberate mapping (the protocol field is already source-agnostic; only the `normalize` read is Claude-specific).
- Two independent presenters both demonstrate a need for a daemon-side *derived* location field (a `repo`, `project`, or `branch`) in their cookbook examples — the reaction-enum-style two-presenter demand bar from §"Substrate-not-actor invariants." Until then, derivation stays in the presenter.
- A presenter need emerges for sub-session cwd history (the *sequence* of directories a session visited) rather than the current/last value — that would be a query over `events.cwd`, not a projection field, and warrants its own design.
