## Context

`Ended` is a daemon-observed liveness state and, per ADR-0004, **non-terminal**: a session can leave `Ended` on the next hook event (typically `UserPromptSubmit` from `claude --resume`). Because a session can always revive, the daemon cannot delete-on-death, so `SELECT_NON_SENTINEL_SESSIONS` returns the **entire** session history forever. That full list is dumped on every presenter twice: in the `GET /sessions` REST response, and in the WS snapshot-on-subscribe burst (Story 2.3, one `StateFrame` per existing session on connect).

The 2026-06-01 dogfooding sessions (`docs/dogfooding-feedback.md`, Finding 5) made this concrete: a "134 ended hidden" footer in `bowerbird-deck`, and two independent presenters (deck + pickletown web) each re-implementing the same hide-ended filter client-side. Moving the filter server-side stops the redundant client work and the connect-time burst.

The dogfood-triage proposal (§4.2) scoped this as REST-only query params plus "scope the snapshot-on-subscribe burst by the same predicate," and noted "no ADR" — on the assumption the work was purely additive query parsing. The maintainer chose to honor the proposal's "same predicate" phrasing literally: the snapshot is scoped by a **presenter-supplied predicate**, parameterized identically to the REST filter, defaulting to unfiltered so current behavior is preserved on both surfaces. That requires an optional field on the inbound `ClientMessage::Subscribe`, which **modifies the wire protocol** — an ADR trigger per `docs/bmad/project-context.md` §"ADR triggers" ("Adds, removes, or modifies the wire protocol"). This ADR records that decision.

The alternative the maintainer weighed and rejected (a fixed daemon-side default that always excludes `Ended` from the snapshot, no protocol change) is captured under Alternatives.

## Decision (one sentence)

`GET /sessions` accepts optional `?state=`/`?since=`/`?limit=` query filters (default unfiltered, preserving v1.0 behavior), and the WS snapshot-on-subscribe burst is scoped by an optional presenter-supplied `states` filter on `ClientMessage::Subscribe` (default absent = unfiltered) — both surfaces filter on the same mechanical-fact predicate (the read-time `current_state`), so the presenter expresses intent and the daemon never decides on its own what is "worth" sending.

Specifics:

- **REST `GET /sessions?state=<csv>`** — comma-separated, case-insensitive `SessionCurrentState` tokens (`idle`, `working`, `waitinginput`, `ended`, `unknown`). Applied in Rust against the **read-time-derived** `current_state` (after `current_state_for_read`'s stale-`Working`→`Idle` fallback), so the filter matches the value the response actually carries. Invalid token → `400`. Absent → unfiltered.
- **REST `?since=<updated_at_ms>`** — exclusive lower bound on the `updated_at` column (a recency filter, not an opaque cursor), pushed to SQL. Absent / `0` → no bound.
- **REST `?limit=<n>`** — positive integer SQL `LIMIT` on the ordered, since-filtered row set. Absent → no cap. The `?state=`+`?limit=` interaction is "limit caps the pre-state-filter set, then state filters in Rust," so a page may return fewer than `n` after filtering (documented). `?since=`/`?limit=` are a **recency filter and a row cap, not true cursor pagination** — `?since=` is an exclusive lower bound under `updated_at DESC`, so it cannot page older rows, can split rows tied on the boundary `updated_at` under `?limit=`, and cannot surface a read-time `Working`→`Idle` change (which doesn't bump `updated_at`). A presenter that needs stable exact-N pages still has no cursor; that stays deferred (see Consequences).
- **WS `Subscribe { topic, states }`** — `states` is an optional `Vec<String>` (`#[serde(default)]`, empty = unfiltered) validated daemon-side **per array element** by `parse_states_array`, sharing the same case-insensitive token table (`parse_state_token`) as the REST CSV parser (`parse_state_filter`) — so a comma-bearing element like `"working,ended"` is rejected rather than split (one wire value, one grammar input, the discipline `topic` follows). An invalid token closes the connection with a `bad message` per the existing invalid-topic path. A non-empty `states` is valid **only on a `state.session.*` family topic** (the only topics with a snapshot to scope); a `states` filter on an event topic closes with `bad message` rather than being silently ignored — accepting it would silently discard the presenter's intent, which the strict-inbound axiom forbids (pass-3 decision). When non-empty, the snapshot-on-subscribe burst includes only sessions whose read-time `current_state` is in the set. **The live stream after subscription is unaffected** — `states` scopes only the initial unsolicited snapshot, never live `state.*`/`events.*` delivery.
- **No retention/eviction.** This filters; it never deletes a projection row. `Ended` rows persist (ADR-0004 non-terminal); the retention sweep stays the no-list "no `bowerbird gc`" cut (bean `gt-3cnt`).

## Alternatives considered

- **Daemon-side fixed default: `snapshot_for_topic` always excludes `Ended`, no protocol change** (the lighter "approach B"). Rejected in favor of the presenter-controlled shape, though it was close. B is a three-line change with no ADR and matches the proposal's stated file footprint, and both current presenters would be happy with it. But it has the daemon *decide* that `Ended` isn't worth bursting — a mild Axiom-1 smell (the substrate making a relevance judgment) — and it *silently changes* the WS snapshot default, breaking the "nothing filters unless you ask" symmetry the REST half preserves. A presenter that legitimately wants the graveyard on the snapshot (a tombstone/audit view) loses that capability under B and must fall back to REST. The presenter-controlled shape keeps the daemon a pure fact-filter (it filters by the mechanical `current_state` the presenter named, exactly like `topic` scopes by session id), preserves presenter control, and keeps both surfaces' defaults identical. The cost (a wire change + this ADR + a `type: schema` changelog entry) was judged worth the axiom-cleanliness and symmetry for a protocol-stability release.
- **`?state=` filtered in SQL via `json_extract(state, '$.current_state')`.** Rejected: `SessionListItem.current_state` is contractually the **read-time** value (stale-`Working`→`Idle`, Story 1.6), not the stored value. A SQL filter on the stored JSON would return rows whose rendered `current_state` contradicts the filter (a stale-`Working` row matching `?state=working` but rendering `Idle`). Filtering in Rust right after `current_state_for_read` guarantees the filter matches what the presenter sees. The cost (state-filter can't shrink the SQL scan; only `since`/`limit` do) is immaterial at the projection's scale (one row per session). The `Ended` partition — the actual use case — is exact either way, because `current_state_for_read` never produces or consumes `Ended`.
- **`states` typed as `Vec<SessionCurrentState>` on the wire instead of `Vec<String>`.** Rejected: `SessionCurrentState` decodes permissively (`#[serde(other)] Unknown`), so a typo'd token would silently become an `Unknown`-filter rather than a loud rejection, and it would force PascalCase from clients. Keeping `states: Vec<String>` and parsing it daemon-side mirrors how `topic: String` is a dumb string parsed by `Topic::parse`, gives one shared token table (`parse_state_token`) for both REST (`parse_state_filter`, CSV split) and WS (`parse_states_array`, per-element) — case-insensitive, typo → reject — and keeps validation where the daemon already rejects bad inbound messages.
- **REST-only now; defer the WS half to a later story** (approach C). Rejected: Finding 5 explicitly named *both* the REST fetch and the snapshot burst; shipping only REST leaves the deck's connect-burst unfixed and the dogfooding win partial. Story 5.8 gates v0.1.0, so the WS decision is due now regardless — deferring moves the work, it doesn't avoid it.
- **Evict `Ended` rows (retention sweep) instead of filtering.** Rejected / out of scope: `Ended` is non-terminal (ADR-0004), so eviction risks losing a session that revives; managed truncation is the no-list "no `gc`" cut. Filtering gives presenters the same relief (no graveyard in their view) without the daemon deleting observable history. Tracked on `gt-3cnt` for a post-V1 reconsideration gated on real growth pressure.

## Consequences

- **Additive and backward-compatible on both surfaces.** REST params default unfiltered (a pre-5.8 caller's request is byte-identical). The WS `states` field is `#[serde(default)]` empty — a v1.0 presenter that omits it gets the current full snapshot. One `type: schema` entry in `docs/protocol-changelog.md` covers the `ClientMessage::Subscribe` field; the REST query params ride the same entry as additive behavior.
- **Forward-compat edge (the known cost of the wire change).** `ClientMessage` is strict (`deny_unknown_fields`); a *newer* presenter sending `states` to an *older* daemon is rejected (WS close 1008). This is the unusual "client ahead of daemon" direction and is acceptable — presenters are expected to match or lag the daemon they connect to.
- **The daemon stays a pure fact-filter.** Both surfaces select rows by the read-time `current_state` the presenter named; the daemon never decides relevance on its own. The snapshot scoping is the same shape as topic scoping (`topic` selects by session id; `states` selects by current_state) — consistent with the substrate-observes-not-interprets axiom.
- **Live delivery is untouched.** `states` scopes only the initial snapshot burst. A session that transitions to/from `Ended` after subscription still produces a live `state.*` frame per Story 5.2's transitions-only gating. A presenter that filtered `Ended` out of its snapshot will still see a session *become* `Ended` live (and can drop it then), and a revived session reappears on the live stream.
- **`?state=`+`?limit=` can return fewer than `limit`.** Because `limit` caps the pre-state-filter SQL set, state-filtering may remove some of the fetched rows. Documented; a presenter needing exactly-N pages via `?since=`. This is a deliberate simplicity choice over a filter-then-limit SQL path that would have reintroduced the json_extract problem.
- **Partially addresses the deferred-work `/sessions` pagination item.** The "No pagination on `GET /sessions`" deferred entry is *downgraded, not closed*: `?since=`/`?limit=`/`?state=` kill the unbounded-response pain (a triage presenter fetches a small filtered set), but **true cursor pagination over `GET /sessions` remains deferred** — `?since=` is a recency bound, not a forward/backward cursor (no stable exact-N paging; tuple-cursor over `(updated_at, source, session_id)` plus direction is the deferred fix, same shape as `/events`). The sibling "No page-size limit on `GET /sessions/{id}/events`" entry is a *different* endpoint and also stays deferred.
- **No schema change, no migration.** This is a query/transport-shape story; `events` and `session_projections` are untouched. (Contrast ADR-0006, which needed migration v3 for `cwd`.)
- **`gt-3cnt` is half-resolved.** The filter half lands here; the retention sweep stays open as a post-V1 deferral.

## Revisit when

- A second adapter ships and presenters need to filter sessions by `source` as well as `state` — `?source=` (REST) and a `sources` field (WS) would extend the same predicate shape; the multi-source disambiguation deferred-work item already tracks the related `/sessions/{id}` ambiguity.
- Projection growth (not event-log growth) actually justifies an `Ended` retention sweep — revisit `gt-3cnt` and the no-list "no `gc`" cut, gating any sweep on history-completeness the way the Story 5.6 reprojection deferral is gated.
- A presenter demonstrates a need to scope the *live* stream (not just the snapshot) by state — that would extend `states` to live delivery, a larger change to the per-client dispatch loop that this ADR deliberately does not make.
- The `?state=`+`?limit=` "fewer than limit" behavior proves confusing enough in practice to justify a filter-then-limit query path (accepting the read-time-vs-stored reconciliation cost that motivated the Rust-side filter).
